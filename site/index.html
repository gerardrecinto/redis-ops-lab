The lock race that a TTL cannot prevent

Worker A takes a lock, stalls past its TTL, and wakes up still believing it owns it. Worker B legitimately took the lock in between. Replay it with and without a fencing token. Topology

  
redis-primary   requirepass, AOF, maxmemory 100mb, allkeys-lru
  +-- redis-replica-1   replicaof primary, read-only
  +-- redis-replica-2   replicaof primary, read-only

sentinel-1, sentinel-2, sentinel-3   quorum 2
  watch the primary, promote a replica on failure

test-runner   python:3.12-slim on the same Docker network

  
All three Sentinels share one Docker host, so they share one failure domain. The repo's tiers doc says plainly that this shows Redis and Sentinel mechanics, not the operations of independently failing machines.






  
Two real incidents

  

    
Sentinel addresses do not resolve from the host
On Docker Desktop for Mac the host cannot route to container bridge IPs, so a client asking Sentinel for the primary got an address it could not reach. Fix: run tests and scripts from a container on the same Docker network, which is also closer to production.

    
Sentinel started before DNS could resolve the primary
depends_on waits for a container to start, not for its hostname to resolve.
Failed to resolve hostname 'redis-primary'
*** FATAL CONFIG FILE ERROR ***
Fix: sentinel resolve-hostnames yes plus a retry loop before each Sentinel launches.

  pip install -q -r /app/requirements.txt

  pip install -q -e /app

What this does not do
    
    
  • The lock and limiter panels above are models, not Redis. Only the failover transcript and the tests list come from the repo itself.
    • 
    
  • The author's README states Redis experience came from running AI infrastructure, not clustering. This lab is where the hands-on failover work happened.
    • 
    
  • Nothing here is deployed on AWS ElastiCache. infra/elasticache.tf is a reference, never applied.
    • 
    
  • A single-instance lock is not a safe lock under every failure. That is the reason for the fencing token.
